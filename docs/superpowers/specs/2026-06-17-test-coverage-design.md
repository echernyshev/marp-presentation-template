# Система покрытия тестами и готовность к TS-миграции — Дизайн

**Дата:** 2026-06-17
**Ветка:** `test-coverage`
**Статус:** предложен (на ревью)

## Контекст и цель

Проект `create-marp-presentation` планируется мигрировать с JavaScript (CommonJS) на TypeScript. Миграция переписывания JS→TS небезопасна без сети безопасности: тесты должны ловить изменение поведения при переписывании. Поэтому **до миграции** нужно построить надёжное покрытие тестами.

Эта спека описывает **фазу покрытия** — предшественницу фазы TS-миграции:

1. Оценить текущее покрытие.
2. Внедрить систему измерения покрытия.
3. Измерить baseline.
4. Поднять покрытие до целевого уровня (поэтапно, через рэтчет).
5. Зафиксировать критерий готовности к миграции.

TS-миграция — **отдельная следующая фаза** со своей спекой; здесь она только как мотивация и потребитель результатов.

## Текущее состояние (baseline)

**Стек:** чистый CommonJS Node.js (`require`/`module.exports`, JSDoc-аннотации типов), Jest 29, `maxWorkers: 1`, без babel/ts-jest. ~2 800 строк исходного JS, ~5 800 строк тестов. Системы покрытия **нет**: `npm test` = `jest` (без `--coverage`); конфига покрытия нет; `coverage/` и `.nyc_output/` уже в `.gitignore`. CI нет (только локальные прогоны).

**Важно про окружение:** runtime-зависимости (`gray-matter`, `@inquirer/prompts`, `fast-glob`) были не установлены (`node_modules` отсутствовал), из-за чего 10 из 15 test-suite'ов падали при загрузке с `Cannot find module`. После `npm install` **все 372 теста проходят (15 suite'ов зелёные)**. Этот baseline снимался на зелёном наборе.

## Зафиксированные решения

1. **Scope (что измеряем и гейтим):** весь JS — `index.js` + `cli/**` + `lib/**` + `template/scripts/**`.
2. **Цель:** 90% строк/утверждений/функций, 80% веток (глобально).
3. **Контроль:** локальный гейт через `npm run test:coverage`; `npm test` остаётся быстрым без покрытия; **CI не вводим** (на будущее).
4. **Инструмент:** встроенный в Jest Istanbul — **0 новых зависимостей**.
5. **Стратегия подъёма порога:** **рэтчет** — порог = baseline (зелёный с первого дня), поднимается по мере добавления тестов.

## Дизайн

### 1. Система измерения

Изменения секции `jest` в корневом `package.json`:

```json
"jest": {
  "testEnvironment": "node",
  "testMatch": ["**/tests/**/*.test.js"],
  "maxWorkers": 1,
  "setupFilesAfterEnv": ["<rootDir>/jest.setup.js"],
  "collectCoverageFrom": [
    "index.js",
    "cli/**/*.js",
    "lib/**/*.js",
    "template/scripts/**/*.js"
  ],
  "coverageDirectory": "coverage",
  "coverageReporters": ["text", "text-summary", "lcov", "html"]
}
```

Скрипты:

```json
"scripts": {
  "test": "jest",
  "test:coverage": "jest --coverage"
}
```

Свойства:
- `collectCoverageFrom` и `coverageThreshold` действуют **только с `--coverage`** → `npm test` остаётся быстрым (покрытие не считается).
- Репортёры: `text` (таблица в консоли), `text-summary` (одна строка), `lcov` (готов для будущего CI/codecov), `html` (браузерный отчёт `coverage/index.html` для поиска дыр).

### 2. Порог и рэтчет

`coverageThreshold` (только в связке с `--coverage`) ставится на baseline, округлённый вниз, чтобы гейт был **зелёным с первого дня** с небольшим запасом:

```json
"coverageThreshold": {
  "global": {
    "branches": 70,
    "functions": 84,
    "lines": 73,
    "statements": 73
  }
}
```

**Рэтчет-цикл** (повторять до цели):

1. Взять модуль с дырой (по приоритету из п. 3).
2. Дописать/расширить тесты.
3. `npm run test:coverage` → зафиксировать новые проценты.
4. **В том же коммите** поднять `coverageThreshold` до нового (округлённого вниз) значения.
5. Коммитить тесты и bump порога вместе.

Порог монотонно растёт и всегда зелёный; он запрещает регрессию (нельзя упасть ниже текущего пола).

### 3. Стратегия закрытия дыр

#### 3.1. Корневая причина 0%-модулей

`index.js`, `copy-static.js`, `theme-cli.js` — исполняемые скрипты с **top-level кодом**: при `require()` сразу читают `process.argv`, вызывают функции, дёргают `process.exit()`. Существующие тесты обходят это:
- `tests/cli.test.js` импортирует нижележащие функции (`createProject` и др.) напрямую, минуя диспетчеризацию `index.js`;
- `copy-static.test.js` и `theme-cli.test.js` копируют скрипт в fixture/temp-проект и запускают через `execSync`/spawn в отдельном процессе node.

В обоих случаях инструментированный исходник не выполняется в процессе jest → 0% в отчёте. Спавн-тесты проверяют поведение, но покрытия не дают (отдельный процесс, вне Istanbul).

#### 3.2. Унифицированное решение: «библиотека + тонкая точка входа»

Для каждого из трёх модулей — один механический рефакторинг:

```js
// было: top-level код выполняется сразу при require
const path = require('path');
// ...вся логика на верхнем уровне...
process.exit(1);

// стало: логика в импортируемой функции, точка входа под guard
function main(argv) { /* вся логика; читает argv; возвращает код выхода */ }
module.exports = { main };                    // ← тестируется in-process
if (require.main === module) {                // ← только при прямом запуске
  const code = main(process.argv);
  process.exit(code ?? 0);
}
```

Затем — unit-тесты в процессе: `require('./index.js')` → вызов `main([...])` с поддельным `argv` → проверки поведения/кода выхода. Istanbul видит выполнение → покрытие.

**Двойная польза:** этот же рефакторинг — ровно то, что нужно для TS-миграции (типизированная `main(argv: string[])`). Фаза покрытия бесплатно готовит код к миграции.

#### 3.3. Безопасность рефакторинга (характеризационные тесты)

У 0%-модулей сейчас нет тестов-сторожей. Порядок безопасный:

1. Сначала спавн-тесты текущего поведения (argv → вывод/код выхода) — фиксируют «как работает сейчас».
2. Рефакторинг в `main()` — спавн-тесты должны остаться зелёными.
3. In-process-тесты для непокрытых веток → покрытие растёт.

#### 3.4. Приоритеты

| Приоритет | Модуль(и) | Обоснование |
|---|---|---|
| **1** | `copy-static.js` → `index.js` → `theme-cli.js` | 199 непокрытых строк (71% разрыва). Без них глобальную цель (90/80) не достичь. Порядок внутри — от малого к большему: 26 → 58 → 115 строк (обкатать паттерн на маленьком). |
| **2** | `lib/theme-manager.js` | Самое низкое branch-покрытие в lib (56.8%, 19 непокрытых веток). |
| **3** | `cli/commands/create-project.js` | Ветки 67.7%, функции 75% — закрыть пропущенные пути. |
| **4** | Добивка остальной lib/cli до per-file пола (80% веток / 85% строк) | `add-themes-command`, `example-resolver`, `add-themes-cli`, `vscode-integration`, `theme-resolver`, `prompts`, `prompt-utils` — точечные тесты по html-отчёту. |

#### 3.5. Конвенции тестирования

- In-process unit-тесты для покрытия; спавн/integration-тесты остаются для end-to-end проверки.
- Branch-targeted: по `coverage/index.html` находим непокрытые ветки → тест на каждую.
- Следуем существующей структуре (`tests/unit/`, `tests/integration/`) и стилю (русские описания вида «должен …»).

## Критерий готовности к миграции (Definition of Done фазы покрытия)

- Глобально все 4 метрики ≥ цели: строки/утверждения/функции ≥ 90%, ветки ≥ 80%.
- **Per-file минимум:** каждый файл ≥ 80% веток и ≥ 85% строк — ни один модуль не мигрирует «вслепую». Проверяется по отчёту; ближе к концу закрепляется per-file порогами в jest.
- После этого начинается фаза TS-миграции; тесты работают как сеть безопасности (переписал модуль на TS → тесты остаются зелёными).

## За пределами области (out of scope)

- Сама TS-миграция (отдельная фаза/спека).
- Внедрение CI (GitHub Actions) — отложено; конфиг подготовлен так, чтобы CI подключился тривиально (скрипт `test:coverage` + lcov-репортёр уже есть).
- Установка зависимостей в репозиторий — это окружение (`node_modules`, `package-lock.json` в `.gitignore`); не часть дизайна.

## Риски

- **Рефакторинг 0%-модулей без тестов-сторожей.** Смягчение: характеризационные спавн-тесты *до* рефакторинга (п. 3.3).
- **Покрытие ≠ корректность.** Высокий процент не гарантирует, что тесты проверяют важное; фокус на ветках и поведенческих путях, а не на «закрасить строки».
- **`template/scripts/*` выполняются в контексте пользовательского проекта** (со своими зависимостями). In-process-тесты запускают их в окружении мета-пакета — нужно следить, чтобы тесты не маскировали различия окружения. Смягчение: спавн/integration-тесты в temp-проекте остаются как end-to-end проверка реального контекста.
